# 本地 Web 界面

Web 界面复用 autoreviewer 的配置校验、代码快照、CLI 调度和报告模块。浏览器负责操作和显示；agent CLI、Git、源码读取及模型请求都在运行 autoreviewer 的机器上执行。

## 启动

需要 Python 3.11+，以及已安装的 agent CLI；扫描 GitHub 仓库还需要 Git。在项目根目录运行：

```bash
python -m pip install -e .
autoreviewer ui --open
```

也可以手动打开 `http://127.0.0.1:8765`。静态页面随 Python 包安装，无需 Node.js、前端构建或 CDN。`--open` 尝试打开运行服务的机器上的默认浏览器；在没有桌面环境的机器上，使用命令打印的地址。

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `--config` | `autoreviewer.toml` | 读取及保存非敏感配置 |
| `--data-dir` | `.autoreviewer/ui` | 保存任务历史和报告 |
| `--port` | `8765` | 本机 HTTP 端口 |
| `--open` | 不启用 | 启动后尝试打开浏览器 |

相对路径以启动命令时的工作目录为基准。服务仅监听 `127.0.0.1`。如果指定的配置文件不存在，界面先加载内置模板，点击保存后才创建文件；示例模型 ID 必须替换成平台实际支持的值。

同一个 `--data-dir` 只允许一个 UI 服务写入。第二个实例会报错退出，避免将正在运行的任务误判为中断或覆盖历史。`ui.lock` 文件保留在数据目录中；进程退出后操作系统释放锁，无需删除该文件。

已有配置可以直接使用：

```bash
autoreviewer ui --config autoreviewer.toml --data-dir .autoreviewer/ui
```

界面保存配置会写入 `--config` 指定的文件。若使用 `examples/` 中的配置并保存修改，对应示例文件也会改变；日常使用建议先复制为自己的配置。

## 配置平台、模型和 CLI

1. 设置平台名称、Base URL、API 协议和密钥环境变量名。
2. 添加模型，填写唯一的配置 ID、平台提供的模型 ID，并选择 CLI。
3. 检查 CLI 是否已安装，必要时设置可执行文件路径。
4. 保存配置，选择要使用的模型后开始扫描。

CLI 检测只检查本机可执行文件是否可找到，不验证版本、平台连接、额度或工具调用兼容性。界面不会安装或更新 CLI，也不会自动转换模型协议。

| CLI | 所需协议 |
| --- | --- |
| OpenCode | OpenAI Chat Completions：`openai-chat` |
| Codex CLI | OpenAI Responses：`openai-responses` |
| Claude Code | Anthropic Messages：`anthropic` |
| Gemini CLI | Gemini API：`gemini` |
| 自定义 CLI | 由用户配置的命令处理 |

只有 Chat Completions 接口的平台应选择 OpenCode。更多配置细节见 [CLI 适配说明](cli-adapters.md)。

API Key 可以通过启动服务时的环境变量提供，也可以在界面中输入。界面输入值仅保留在本次服务进程内存中，优先于同名环境变量；清除本次输入后重新使用环境变量。浏览器不会在本地存储中保存密钥，服务不会把密钥值返回给界面。停止或重启服务后，需要重新输入会话密钥。

配置文件仅保存密钥的环境变量名，并以私有文件权限写入。不要将密钥放到 Base URL、模型 ID、CLI 参数或其他普通文本字段中。

多个浏览器页面编辑配置时，保存会校验配置版本。旧页面的修改不会覆盖另一页面刚保存的内容；冲突提示会保留当前输入，请先复制需要保留的修改，再重新加载并编辑最新配置。

“导出配置”可下载当前非敏感 TOML。导出内容包含平台、模型、CLI、扫描设置和可选 GitHub 配置，密钥仅以环境变量名表示；会话凭据和环境变量中的密钥值不会写入导出文件。

## 发起和查看扫描

填写本地目录，或 `https://github.com/OWNER/REPO`。本地目录位于**服务运行的机器**上；浏览器不会上传另一个电脑中的目录。GitHub 目标可指定分支或标签。私有仓库需要配置相同的 GitHub 仓库地址及具有 Contents 读取权限的 token。

选择模型、并发数和单模型超时后启动。当前只允许一个扫描任务处于活动状态，但一个任务可以并行运行多个独立 CLI 实例。每个实例拥有独立过滤代码副本、配置、缓存和临时目录。

任务详情显示各模型的排队、运行、完成、失败和超时状态。活动记录显示这些真实状态变化及已脱敏错误，不显示模型完整思考过程或原始 stdout。刷新浏览器后可以重新进入任务，不需要重新启动扫描。

模型结束时，服务保存包含当前发现的阶段检查点。无需等待其他模型全部结束，就可以查看、筛选及下载阶段结果。阶段报告带有 `checkpoint: true`；正在运行的任务仍显示运行状态，阶段结果不能视为完整审计，也不能在任务运行期间发布 Issue。

取消任务会请求停止当前分析并清理模型进程，保留已经完成的结果。GitHub 克隆也支持取消；正在复制代码快照时，需等待当前复制步骤返回。

## 中断恢复和重试

服务重启后，未完成的任务显示为中断。若存在有效检查点，会恢复其中已完成模型的发现，并把未完成实例标为 `interrupted`；不会自动重新调用模型。检查点通过原子替换保存，但没有提供断电后的持久化保证。尚未写入检查点的结果、正在生成的回答，以及磁盘写入失败时的结果可能无法恢复。界面会显示保存失败提示，仍在内存中的结果可以尝试下载。

最终报告损坏时，恢复流程会继续尝试有效检查点，并显示恢复提示；被拒绝的报告会尝试保留为 `report.unreadable-<标识>.json`。报告与检查点均不可用时，界面明确提示无法恢复，不会把缺少结果显示为成功审计。

终态任务可以选择“重试失败模型”或“重新扫描”。前者只选择失败、超时、取消或中断的实例，后者选择原任务的全部实例。操作会创建关联原任务的新任务，原报告和原运行状态保留。

重试会重新读取目标路径或 GitHub 引用并创建新代码快照，使用当前配置中的并发与超时设置，以及当前可用凭据。所选实例的配置 ID、平台、模型名称和 CLI 必须与原任务一致；如果被删除或修改，先检查配置，再从“新建扫描”明确选择模型。重试不会把两次不同代码快照的发现拼成一次审计。导入的报告不提供重试入口。

## 审阅结果和导出

按严重程度、模型或文件筛选发现，查看描述、代码证据、建议、来源模型和运行结果。JSON 和 Markdown 下载包含同一份报告；模型失败或超时不会转换为“没有发现问题”。

同一指纹包含多个模型观察时，展开后可以分别查看每个模型的描述、证据、置信度及修复建议。模型筛选只展示该模型的观察；发现的汇总严重程度仍取所有来源中的最高值。Markdown 和 Issue 预览也保留这些逐模型证据。

启用“同位置候选组”后，同一文件、相同行号和相同非空 CWE 的记录会放在一起，便于比较不同模型的证据。缺少 CWE 的记录独立显示。分组不执行语义去重，不证明记录属于同一个漏洞；原始记录数、指纹、模型观察和逐条选择发布的能力均保留。

发现仍是待人工核实的线索。多个模型提出相同问题不等于验证成功；标题不同的相似发现也可能保留为多条记录。报告中的严重程度和修复建议来自模型，需要结合代码和部署情况复核。

默认数据目录结构为：

```text
.autoreviewer/ui/
  ui.lock
  jobs/
    <任务 ID>/
      job.json
      checkpoint.json   # 运行中的阶段结果；最终报告保存成功后清理
      report.json
      report.md
```

任务历史和报告会保留到后续启动。报告可能包含源码片段，请按项目敏感程度管理该目录的访问和保留时间。临时代码副本与 agent 状态在任务结束时清理。

## 导入已有报告

在任务概览选择“导入 JSON 报告”，打开此前由 CLI 或界面导出的 JSON 文件，文件上限为 32 MiB。服务校验报告结构、状态一致性、指纹以及模型来源，保存为单独的导入任务，并保留来源文件名。报告中的目标路径只是说明文字，导入不会读取该路径、运行命令或调用模型。

导入报告可以筛选、分组、导出，并在明确预览和确认后发布选中的 Issue。导入不验证源码是否与报告一致，也不证明报告来自可信模型。仍需人工核对内容；格式通过校验不等于漏洞通过验证。包含有效检查点标记的阶段报告可作为中断结果查看，未完成实例不会被当成成功运行。

## GitHub Issue

在 GitHub 配置中指定 `OWNER/REPO`、token 环境变量名及可选标签，配置的标签必须已存在。私有源码读取需要 Contents: Read；发布 Issue 需要 Issues: Read and write，token 应限定到目标仓库。

任务结束后，审阅报告并选择要提交的发现，生成 Issue 预览，检查目标仓库、标题和正文，再明确确认发布。预览本身不会调用 GitHub 创建接口；扫描、重试和导入也不会自动发布。部分模型未完成的报告需要显式允许部分结果，全失败报告不能发布。

每次最多选择 1,000 条发现进行预览，超出时需减少选择。单条 Issue 正文超过 GitHub 的 65,536 字符限制时，会提示下载完整报告并人工整理，不会截断模型证据。

发布流程沿用报告指纹检查已有 Issue。指纹匹配不等于语义去重；措辞不同的同一问题可能仍生成不同条目。公开 Issue 会公开正文中的漏洞细节，敏感问题应通过目标仓库的私密报告渠道处理。

成功发布的回执保存在任务历史目录的 `github-publications.json`，只包含仓库、指纹及 Issue 编号，不含 token。重启后会按编号直接核对已发布 Issue，避免列表漏项引起重复创建；关闭的 Issue 保持关闭。回执损坏、远端条目不可访问或指纹标记改变时会停止发布并提示核查。此保护依赖保留同一回执文件，不保证独立客户端同时发布的全局幂等性。[真实 GitHub 实测](live-tests/github-2026-10-23.md)验证了创建、立即重发及关闭后重启再发。

## 不调用真实模型的演示

从项目根目录运行：

```bash
autoreviewer ui --config examples/demo.toml --data-dir .autoreviewer/ui-demo
```

在界面中将目标设为 `examples/demo-repository`，选择两个演示模型后开始扫描。演示仅运行本机 Python fixture，不需要 API Key、不访问模型平台，也没有进行真实代码分析。它返回明确标记为 `DEMO ONLY` 的固定发现，用于体验调度、结果审阅和导出流程。

此前 NVIDIA 八并发真实测试记录见 [并发实测记录](live-tests/nvidia-parallel-2026-10-22.md)。那次测试早于 Web 界面加入；不能将演示或浏览器流程测试视为新的真实模型审计验证。

## 界面验证

当前 225 项 Python 自动化测试已通过。Chromium 浏览器测试跑通了配置编辑与导出、会话凭据、双实例扫描、阶段结果查看与下载、报告导入、失败模型重试、候选分组、结果筛选、两种报告下载、明确确认后的模拟 Issue 发布、取消、服务重启后的历史读取、模型输出 HTML 转义，以及 390 像素窄屏布局。测试使用本地 fixture CLI，没有调用真实模型或创建 GitHub Issue。复现命令见 [贡献指南](../CONTRIBUTING.md)。

独立体验反馈还补充了浏览器回归：双页面配置冲突、跳转主内容与焦点恢复、延迟响应期间的导航及表单保留、扫描按钮状态更新、逐模型证据筛选、发布数量限制和文字对比度。320、390、768 像素页面也经过实际浏览器检查。

另已离线验证此前真实八模型报告的导入和重启后读取：保留八个运行状态（五个完成、两个失败、一个超时）及十条发现，显示两个同位置候选组，原报告未改动，没有新增模型 API 调用。

## 运行边界

这是供单个本机用户使用的界面，没有公共网站所需的多用户身份认证和权限隔离。请勿将其通过公网代理或端口转发公开。CLI 配置可启动本机程序，只应使用信任的命令。

工作目录与 CLI 工具权限隔离不等于操作系统或容器沙箱。各进程仍以服务用户运行，并向选定平台发送代码。API Key 留在内存也不构成加密密钥保管库。完整说明见 [SECURITY.md](../SECURITY.md)。
