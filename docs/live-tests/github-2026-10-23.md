# GitHub 集成实测：2026-10-23

使用用户指定的测试仓库 [zhuhanxin0308/clipboard.js](https://github.com/zhuhanxin0308/clipboard.js)，验证真实 Git 拉取、Issue 创建、完整正文、重复发布和关闭后的去重。最终回执方案通过实测；前两轮确实出现重复创建，失败记录保留。

## 范围

- 日期按 Asia/Shanghai（UTC+8）记录。
- 应用通过真实 GitHub HTTPS 拉取默认分支，两个离线 fixture CLI 读取实际 `readme.md`，生成一个明确标注 `TEST ONLY` 的合并发现，保留两份不同来源的观察。
- 发布使用产品 `WebService` 和 GitHub HTTP 客户端，没有替换网络请求；另用 GitHub 连接工具独立读取 Issue，逐字核对正文和统计数量。
- 测试没有调用大模型，不评估 clipboard.js 的安全性，也不验证私有仓库访问或此次运行的进程隔离。
- 仓库起初没有启用 Issues。当前连接修改设置返回 403，由用户手动开启后继续。

## 发现及修复

第一轮创建 [#1](https://github.com/zhuhanxin0308/clipboard.js/issues/1)，立即重发却创建了重复的 [#2](https://github.com/zhuhanxin0308/clipboard.js/issues/2)。列表请求曾返回空数组，但按编号读取能看到已创建的 Issue。

增加请求缓存控制后，第二轮 [#3](https://github.com/zhuhanxin0308/clipboard.js/issues/3) 与 [#4](https://github.com/zhuhanxin0308/clipboard.js/issues/4) 仍重复。不同列表查询曾返回不一致的结果；独立连接能读取完整列表。缓存控制和唯一查询参数都不足以解决问题，具体异常发生在哪一层尚未确定，不能声称已定位为 GitHub 缓存故障。

最终修复增加持久发布回执：

- UI 使用历史目录的 `github-publications.json`；CLI 使用报告目录的同名文件。预览不创建回执。
- 回执按仓库和发现指纹记录 Issue 编号，不保存凭据；每条成功结果立即以私有权限原子写入。
- 再次发布时按编号读取已知 Issue，核对指纹标记和编号；不依赖列表是否包含它。
- 回执损坏、存储失败、远端条目不可访问或标记不符时，停止发布并提示核查，不静默重新创建。
- 多条发布部分失败时，已成功条目的回执仍保留。POST 成功但回执保存失败会明确报错并停止后续创建。

#1 至 #5 均为合成测试数据，已关闭。#2 和 #4 标记为重复。没有修改仓库源码。

## 自动化验证与边界

最终 225 项 Python 测试通过，Chromium 浏览器主流程通过。新增测试覆盖列表始终为空时的持久回执、UI 重启、CLI 重复调用、已关闭 Issue、损坏或伪造回执、存储失败和多条发布部分失败。

回执保护依赖保留并复用同一文件。没有回执的独立客户端仍依赖远端列表；并发客户端仍可能竞争。若 POST 已在远端成功但响应丢失，应用可能无法记录其编号，应先核查 GitHub 再重试。此改动不提供跨客户端的全局幂等保证。
